# Lily Consumer

`lily_consumer` is the process composition root for Lily RabbitMQ handlers. It
loads strict Lily configuration, discovers typed handlers generated by
`lily_queue`, resolves their services through Lily DI, opens a fresh DI scope
for each delivery, and owns bounded graceful shutdown.

```toml
[dependencies]
lily_consumer = "0.1.0"
lily_queue = "0.1.0"
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

The `lilyrs` feature `consumer` exposes both `lilyrs::consumer` and
`lilyrs::queue`. The direct component has no default features; optional
AsyncAPI and transactional storage profiles are described below.

```rust,no_run
use lily_consumer::{Consumer, Injectable, ServiceTrait};
use lily_queue::{Json, QueueHandlerError, queue, queue_service};
use serde::Deserialize;

#[derive(Deserialize)]
struct OrderCreated {
    order_id: String,
}

#[derive(Default, Injectable)]
#[service(lifetime = "Singleton")]
struct OrderWorker;

impl ServiceTrait for OrderWorker {}

#[queue_service]
impl OrderWorker {
    #[queue("orders.created", version = 1, content = "json")]
    async fn created(
        &self,
        Json(message): Json<OrderCreated>,
    ) -> Result<(), QueueHandlerError> {
        println!("{}", message.order_id);
        Ok(())
    }
}

#[tokio::main]
async fn main() -> Result<(), lily_consumer::ConsumerError> {
    Consumer::run().await
}
```

Before running, provide a reachable RabbitMQ broker and a Lily configuration
file with the matching `rabbitmq` connection and `rabbitmq.topology.queues`
entries. Set both `LILY_CONFIG_PATH` and `LILY_CONFIG_MODE` (`development`,
`test` or `production`). The [connected examples](../../../examples/README.md)
include Compose, shared services and a complete Consumer configuration.
The Rust snippet declares the handler; it does not provision a broker.

Every configured `[[rabbitmq.topology.queues]]` entry must have at least one
matching linked handler. Multiple handlers may share the physical queue when
their `(schema version, content kind)` pairs are unique. The Consumer opens one
RabbitMQ consumer pipeline for the queue and freezes those handlers into one
immutable local dispatch table. Linked handlers without a configuration entry
remain inactive. Concurrency, prefetch, retry, retention and topology policy
belong to configuration, never to the handler attribute.

An exact duplicate dispatch key anywhere in the linked binary is still a
startup error, including for an inactive queue. This preserves one
unambiguous registry authority for runtime dispatch and documentation; config
selects which queues are active, not which duplicate metadata record wins.

### Optional AsyncAPI 3.1 snapshot

Enable the `asyncapi` feature on both canonical application dependencies. The
Consumer feature activates the matching queue macro/runtime feature; Cargo
feature unification makes the direct `lily_queue` import use that same ABI.

```toml
lily_consumer = { version = "0.1.0", features = ["asyncapi"] }
lily_queue = { version = "0.1.0", features = ["asyncapi"] }
```

Document intent belongs to the same `#[queue_service]` / `#[queue]` metadata
that runtime dispatch accepts. Service metadata is inherited; handler metadata
may refine it or explicitly skip one handler. Built-in `Json<T>`,
`TextPayload`, and `BinaryPayload` extractors infer their schema/content type.
`Json<T>` requires `T: lily_consumer::schemars::JsonSchema`. The derive is
re-exported through the same facade; importing `schemars::{self, JsonSchema}`
puts both the derive and its generated runtime path in scope. Applications do
not select a different schema implementation. A raw, custom, or body-unobserved handler must declare either
`schema = WireType, content_type = "..."` or
`opaque, content_type = "..."`; Lily does not invent a payload contract.

```rust,ignore
use lily_consumer::{
    AsyncApiConfig, AsyncApiServer, AsyncApiServerProtocol, AsyncApiTag,
    Consumer,
};
use lily_consumer::schemars::{self, JsonSchema};
use lily_queue::{Json, QueueHandlerError, asyncapi, queue, queue_service};
use serde::Deserialize;

#[derive(Deserialize, JsonSchema)]
struct OrderCreated {
    order_id: String,
}

#[queue_service]
#[asyncapi(tag = "orders")]
impl OrderWorker {
    #[queue("orders.created", version = 2, content = "json")]
    #[asyncapi(
        operation_id = "consumeOrderCreatedV2",
        summary = "Apply an order-created event",
        example = r#"{"order_id":"order-42"}"#
    )]
    async fn created(
        &self,
        Json(event): Json<OrderCreated>,
    ) -> Result<(), QueueHandlerError> {
        let _ = event;
        Ok(())
    }
}

let mut document = AsyncApiConfig::new("Order consumer", "2.0.0")?;
document.add_tag(AsyncApiTag::new("orders")?)?;
document.add_server(AsyncApiServer::new(
    "production-rabbitmq",
    "rabbitmq.example.com:5671",
    AsyncApiServerProtocol::Amqps,
)?)?;

Consumer::builder().asyncapi(document).run().await?;
```

The generated receive operations come only from the accepted local execution
plan. Their queue, exchange, routing, retry/DLQ, managed/external,
classic/quorum and exact `(schema version, content kind)` values come from the
effective RabbitMQ topology and dispatch authorities. Required Lily envelope
headers are documented exactly. Transactional handlers identify only their
selected PostgreSQL or MongoDB local transaction boundary; the document does
not claim broker/database 2PC or global exactly-once delivery.

After successful startup, an application sharing the Consumer's DI container
may resolve `lily_consumer::ConsumerAsyncApiService` and return
`canonical_json()` from its own HTTP action. Lily intentionally registers no
endpoint, file exporter or UI. Omitting `.asyncapi(...)` registers no service,
and using `#[asyncapi(...)]` without the Cargo feature is a targeted compile
error rather than silently discarded metadata.

Delivery metadata, services and local context are body-free typed extractors;
at most one payload extractor may appear and it must be the final argument.
Handlers classify application failures explicitly as retryable or permanent.
Lily does not infer this class from `ServiceError`: an application error must
implement `Into<QueueHandlerError>` deliberately. Decode, extraction and exact
schema/content mismatches are fail-closed before application handler code.
Missing canonical event/version/content headers are invalid deliveries; Lily
does not treat them as implicit V1 JSON. An unknown version or content kind is
a permanent typed rejection before a delivery scope or application pipeline is
created.

Built-in content contracts are `json` (`Json<T>`), `text` (`TextPayload`) and
`binary` (`BinaryPayload`). `RawDelivery` exposes bounded raw bytes/metadata
under an explicitly declared content token, while a custom `FromDelivery`
extractor owns application-specific decoding. Body-free handlers also retain
an exact declared token, commonly `none`.

Application-defined middleware and guards are opt-in. Register global types
with `Consumer::builder().middleware::<M>()` and `.guard::<G>()`; service and
handler types use repeatable `#[middleware(Type)]` / `#[guard(Type)]` markers
below the outer `#[queue_service]` attribute. Every effective middleware runs
first in global, service, handler order; guards then run in their own global,
service, handler order. Middleware unwinds only its successfully entered prefix
in reverse before DI cleanup and broker settlement. Constructors run once per
Consumer build; scoped/transient dependencies are resolved from the
per-delivery `QueueDeliveryExchange`.

Consumer startup is owned by one private build transaction. For
`run_with_cancellation()`, the supplied token is observed while Lily builds DI,
resolves configuration, compiles the middleware/guard plan and registers
physical queues—not only after readiness. Cancellation first drops the pending
startup future, then stops queue admission, drains/closes the acquired queue
runtime, disposes only a framework-owned container and finally shuts down only
framework-owned tracing. A caller-supplied container and external tracing
runtime remain caller-owned, although the Consumer still closes the queue
runtime it started from that container.

An explicit startup failure awaits this rollback and retains cleanup failures
as typed secondary evidence. Dropping or aborting the caller future cannot
await, so ownership is moved to one bounded cleanup task on the Tokio runtime
which originally polled startup. That guarantee requires the captured runtime
to remain alive until cleanup completes. A still-pending DI build uses the
independent `lily_injection` build-rollback budget (30 seconds by default, or
`LILY_INJECTION_BUILD_ROLLBACK_TIMEOUT_SECS`); after DI has completed, Consumer
cleanup uses the application lifecycle shutdown budget, falling back to 30
seconds until configuration has been resolved.

After a successful build, the committed transaction transfers every runtime
cleanup resource synchronously, with no intervening `.await`, into one private
`ConsumerRuntimeOwner`. That owner is the sole cleanup authority after
readiness. The queue runtime, shutdown state, optional signal monitor,
lifecycle budget, captured Tokio runtime handle, and only the framework-owned
DI and tracing owners are moved together into one supervised task before
runtime waiting begins. This is an internal lifecycle boundary; it does not add
a public cleanup API or change delivery execution.

`run()` and `run_with_cancellation()` retain and await that supervisor. If the
outer future is dropped or aborted, its armed guard requests durable `Manual`
shutdown through the shared shutdown state; it does not abort the supervisor.
The owned task can therefore finish the canonical bounded cleanup even after
the caller waiter has gone away. Any asynchronous `Drop` fallback uses the
captured Tokio runtime and is guaranteed only while that runtime remains alive.
Provider termination, OS signals, caller cancellation, managed shutdown,
managed readiness-waiter loss, and outer-waiter drop all converge on this same
owner and shutdown coordinator rather than creating a second cleanup authority.
Caller-owned DI and external tracing are neither transferred into the cleanup
owner nor shut down by it, while the queue runtime acquired from a caller-owned
container remains Consumer-owned and is still closed.

Each admitted delivery receives an isolated cooperative cancellation token and
absolute deadline. ACK/retry/DLQ materialization happens only after its DI
scope has completed asynchronous cleanup. Queue attributes and runtime
closures cannot bypass this path; `#[queue_service]` + `#[queue]` metadata is
the sole handler-registration authority.

Multiple replicas of the same Consumer binary safely share a queue as normal
RabbitMQ competing consumers. A mixed fleet has a stricter invariant:
RabbitMQ does not inspect Lily schema/content headers when selecting a
consumer, so every process on the physical queue must support every key that
publishers can emit. For an expand-contract rollout, deploy old+new handlers
everywhere before enabling new-version publication. Use separate physical
queues/routing bindings for intentionally incompatible version-specific
binaries.

### Optional PostgreSQL effectively-once processing

PostgreSQL inbox/outbox support is default-off. Select exactly one of
`transactional-inbox-postgresql` or
`transactional-inbox-postgresql-factory`, mark the handler with
`delivery_guarantee = "transactional_inbox"`, and add a matching queue-level
`transactional_inbox` policy. Lily reuses the PostgreSQL service or exact
factory cell already owned by the application container; it does not create a
second container, pool or configuration authority.

These canonical Consumer features enable the matching `lily_postgresql` DI
registration mode. The corresponding low-level `lily_queue` adapter feature
only compiles the transaction API; it does not become a second database
registration authority.

The framework-owned schema is installed only through
`lily_queue::PostgresInboxOutboxMigrator` in an explicit deployment job.
Ordinary Consumer startup performs a read-only compatibility check before
listener admission. A missing feature, binding, cell or schema is a typed
startup failure and never degrades to at-least-once.

Inside a transactional handler, use the `lily_queue::PostgresTransaction`
parts extractor for every business mutation covered by the guarantee. Its
`enqueue` method writes a validated `TransactionalOutboxMessage` through that
same transaction. Middleware, guards, extraction, the handler, reverse unwind
and delivery-scope cleanup all finish before inbox completion and commit;
RabbitMQ settlement remains the sole downstream ACK/retry/DLQ/NACK authority.
The handler annotation alone does not redirect injected repositories or newly
acquired pool connections through this transaction; those operations remain
outside the guarantee unless the application explicitly runs them on the
extractor's exact connection.

Inbox deduplication uses the generated
`module_path::ServiceType::method` identity plus the event ID. Renaming or
moving a transactional handler creates a new deduplication namespace, and a
completed identity is remembered only for the configured inbox retention
horizon.

`ManagedConsumer::snapshot()` includes the feature-gated transactional outbox
relay snapshot. An exhausted or terminal relay lowers aggregate readiness and
publishes only stable, payload-free failure evidence. Graceful shutdown stops
transaction/relay admission, reconciles owned database and publish work, and
only then permits RabbitMQ and DI disposal.

Use `Consumer::builder()` for a caller-owned DI container, an application
secret resolver, explicit tracing ownership, cancellation-token hosting, or a
programmatic `ManagedConsumer`. The same builder selects global middleware,
global guards and their bounded aggregate asynchronous constructor timeout
(default 30 seconds; valid range greater than zero through 300 seconds).
Constructors are polled in the composition task rather than detached child
tasks. Cancelling startup therefore drops the pending constructor before the
already initialized middleware/guard prefix is released once in reverse order.
Builder `run()` installs OS signal handlers;
`run_with_cancellation()` and `start_managed()` do not. Every run mode also
returns if the supervised queue runtime terminates naturally or with an error.

`ManagedConsumer` is cloneable. Concurrent `shutdown()`/`wait()` observers
share the retained runtime task and replay one terminal result; cancelling an
observer future does not detach that task. Dropping the final handle only
requests graceful shutdown because Rust `Drop` cannot await. Applications that
need terminal cleanup evidence must await `shutdown()` or `wait()`.

The `start_managed()` readiness waiter has its own armed cancellation guard.
Dropping that waiter before a `ManagedConsumer` is returned immediately cancels
the token observed during startup and by the post-readiness runtime wait; a
successfully constructed handle disarms the guard synchronously. Provider
completion remains the first branch in biased runtime selection, so a
simultaneous shutdown request cannot hide a provider terminal result. Managed
`wait()` and `shutdown()` observers continue to share and replay the same
immutable terminal result, and dropping an observer does not discard the
retained supervisor task.

### Managed operational snapshot

`ManagedConsumer::snapshot()` returns a cloneable, immutable and
JSON-serializable `ConsumerOperationalSnapshot`. It is the canonical
application-facing view of Consumer lifecycle, broker/topology state, delivery
admission, registered queue/handler counts, in-flight work, settlement,
retry/dead-letter counters and bounded shutdown evidence.

```rust,no_run
use lily_consumer::{Consumer, ConsumerError};

#[tokio::main]
async fn main() -> Result<(), ConsumerError> {
    let consumer = Consumer::builder().start_managed().await?;

    let snapshot = consumer.snapshot();
    if snapshot.live && !snapshot.ready {
        // The process is alive, but an orchestrator must not route work to it.
    }

    consumer.shutdown().await
}
```

Liveness and readiness are deliberately separate:

- `Starting` and broker `Recovering` remain live but are not ready.
- `Ready` is reported only while every selected queue is ready and shutdown
  admission remains open.
- `Draining` remains live while accepted work is reconciled, but readiness is
  already false.
- A terminal `Stopped` or `Failed` runtime is neither live nor ready.

A successful reconnect may restore readiness. Retry, DLQ or in-flight activity
alone never does. The snapshot contains no message payload, event ID, routing
key, broker endpoint or credential; `last_failure_code` is a stable bounded
code rather than raw error text. It is historical evidence and remains after a
successful recovery; `ready` is the current admission authority. Runtime
counters are sampled as a best-effort point-in-time operational view, not as a
transactional accounting barrier; lifecycle precedence normalizes terminal and
readiness state. Lily does not register an HTTP health route.
An application may explicitly publish the snapshot through its own endpoint,
metrics adapter or orchestration integration.

`ManagedConsumer::shutdown_report()` returns the final
`ConsumerShutdownReport` after the actual runtime task has joined, including
when `wait()` or `shutdown()` returns an error. The same value is available at
`snapshot().shutdown.report`. Before that join it is `None`; it also remains
`None` if the runtime failed before producing coordinator evidence. Missing
evidence never means successful cleanup.

```rust,no_run
# async fn observe(consumer: lily_consumer::ManagedConsumer) {
let result = consumer.shutdown().await;
if let Some(report) = consumer.shutdown_report() {
    // report.completion distinguishes graceful, forced, failed and incomplete.
    // report.is_success() requires successful cleanup and actual owner barriers.
    println!("{report:?}");
}
if let Err(error) = result {
    eprintln!("{}", error.error_code());
}
# }
```

`shutdown.completed` means the runtime task joined, even if cleanup failed or
remains unconfirmed. The final report separately exposes:

- Original graceful and forced outcomes for each application shutdown action.
  A force completion does not erase the original timeout or panic.
- Delivery/scope/transaction/relay drain and broker-connection close barriers.
- Whether DI, telemetry and the signal monitor were owned, cleanup started,
  actual termination was observed, and disposal succeeded. Caller-owned or
  absent dependencies have `owned = false`; no disposal is claimed for them.
- The shared total budget, elapsed time and stable original failure code.

`Failed` means termination is proven but an operation failed. `Incomplete`
means required resource or action evidence is missing. Late cleanup and repeated
observers cannot rewrite the original report. A lost shutdown waiter does not
lose the retained task or start another attempt. Direct `run*()` callers retain
the typed result/error and lifecycle tracing; the structured report is exposed
through the managed handle. Lily does not emit the report through a hidden
endpoint or require tracing to read it.

The shutdown report keeps one bounded list of application actions (at most five
for this runtime), not one entry per message. Runtime delivery/transaction/relay
aggregates use fixed counters. A separate queue diagnostic API,
`QueueService::delivery_terminal_observations()`, retains **at most 4096**
settlement observations with event IDs and no message payload. These details
are best effort: capacity or lock contention increments `dropped`, without
blocking settlement or removing its aggregate evidence. They are not a complete
delivery audit log. Active execution ledgers, scopes and join receipts scale
with outstanding work; completed receipts are reaped. Incomplete retained owners
are reported as incomplete and can keep resources alive until runtime teardown;
shutdown returning is not an automatic memory reset.

When a transactional backend feature is enabled, the same snapshot includes a
payload-free `transactional_inbox` ledger. It reports active transaction
owners, MongoDB body/commit attempts, bounded replay and unknown-commit counts,
external lease contention, retry exhaustion, and advisory post-commit lease
release failures. These sampling-independent counters contain no handler,
event, database-cell, endpoint or credential identity. A retained
`last_failure_code` is historical diagnostic evidence; it does not by itself
lower readiness after a successful recovery.

Consumer failures use typed, source-preserving and secret-safe
`ConsumerError` variants; there is no catch-all string error. When runtime and
cleanup both fail, `ConsumerLifecycleFailures::primary()` preserves the first
authoritative startup/runtime failure and `secondary_failures()` retains later
shutdown or cleanup evidence in observation order. `Display` and `Debug`
expose bounded error codes, while typed sources remain available through the
error chain for programmatic inspection.

## Optional MongoDB effectively-once processing

Enable exactly one of `transactional-inbox-mongodb` or
`transactional-inbox-mongodb-factory`. These canonical Consumer features also
enable the matching `lily_mongodb` DI registration mode; MongoDB remains absent
from default and PostgreSQL-only builds. Mark selected handlers with
`delivery_guarantee = "transactional_inbox"` and configure the physical queue
with `transactional_inbox.backend = "mongodb"`. Single mode forbids
`database_cell`; factory mode requires one exact configured cell.

The corresponding `lily_queue` feature only compiles the adapter API. It does
not eagerly register a MongoDB service, so a standalone `QueueService`
composition root must explicitly enable and own the selected database mode.

Before starting any listener, an explicit deployment job must apply
`lily_queue::MongoInboxOutboxMigrator` using the selected application-owned
`lily_mongodb::DatabaseService`. Consumer startup performs only read-only
migration and transaction-capability checks. It does not create collections,
indexes, a second MongoDB client or a second configuration authority, and it
does not silently weaken the guarantee on a standalone MongoDB deployment.

The handler receives `lily_queue::MongoTransaction` as a body-free typed
extractor. Use `MongoTransaction::operation_context()` for every business
mutation covered by the inbox transaction and `MongoTransaction::enqueue()`
for durable outgoing events. Independently resolved database writes and all
external side effects are outside the guarantee. `MongoTransaction` is also
handler-body scoped: clones moved into detached tasks are cancelled as soon as
the body returns, so they cannot perform a post-commit database or outbox
write.

A MongoDB `TransientTransactionError` replays middleware, guards, extraction,
handler execution and reverse unwind in a fresh delivery DI scope and a fresh
database session. Application handler code must therefore be replay-safe and
must keep irreversible side effects out of the transaction body. Commit-result
ambiguity is reconciled separately within the bounded
`commit_retry_timeout_millis` policy. If it remains ambiguous, the original
delivery is directly requeued without consuming application retries or DLQ
handoff. RabbitMQ ACK occurs only after a known commit; duplicate redelivery
after an ACK crash is suppressed by the completed inbox identity.

Concurrent delivery of the same handler/event identity waits only inside the
delivery's absolute bounded budget while the first MongoDB lease remains live.
If the first owner commits, the duplicate becomes `AlreadyCompleted`. If the
lease expires, the retained duplicate may acquire it and run. If the delivery
budget expires first, Lily performs one direct broker requeue without consuming
the application retry budget or routing the message to the DLQ. A failed
best-effort lease deletion after a committed result is exposed through the
operational ledger and never rewrites that committed result into a handler
failure.

The outbox relay remains one worker per backend/database cell while every
physical queue runtime retains its own transaction-drain authority. Shutdown
stops all transaction admission and drains every queue runtime before database
DI disposal.

## Forced lifecycle contract

The retained runtime owner uses the same phase-specific forced cleanup as the
normal lifecycle coordinator. If force has already been requested before
cleanup begins, the queue sequence is exactly `stop_admission_async` followed
by `force_drain_async` and `close_async`. Each phase is invoked once; owned DI
and owned tracing cleanup can run only after the queue report reconciles.

The process coordinator anchors the total shutdown deadline to the first
shutdown request; a delayed supervisor cannot restart that budget. Closing
delivery admission does not cancel started handlers. Execution cancellation,
cleanup and settlement have separate framework authorities. During force,
Lily notifies execution and gives the normal delivery pipeline a bounded
cooperative window. A completed pipeline retains its real result; an unfinished
execution slot is dropped while its lifecycle owner performs reverse
`on_delivery_termination` cleanup and exact DI disposal. The dispatcher allows
bounded owner completion before requesting final task abort and confirming joins,
then closes the dedicated channel after subscription cancellation and all
delivery/settlement joins. Healthy-channel settlement stays authorized during
bounded cooperative completion; final abort revokes it before stopping remaining
tasks. The provider reconciles retained delivery lifecycle owners before closing the broker
connection and finally the owned DI container. Each delivery owner preserves
its middleware ledger and exact scope-close result when execution is dropped;
transferred cleanup tasks keep their real join handles. DI disposal is withheld if
task reconciliation cannot be proven; a non-yielding blocking/CPU-bound user
future therefore produces an explicit incomplete shutdown rather than a false
success.

The [lifecycle contract and implementation stages](LIFECYCLE.md) describe the
implemented boundaries and transaction/outbox/dependency
reconciliation rules. Recovery cannot open a replacement subscription until the
old generation's tasks and channel terminate. Settlement and channel operations
share the root deadline, including a shorter root published while they wait.
Preserving the pipeline result does not guarantee broker ACK or transaction
commit; missing settlement or join evidence is never reported as success.

Transaction/outbox shutdown uses the same absolute application deadline as queue
drain. Consumer retains transaction, relay, heartbeat and fallback task joins;
zero active counters alone do not prove shutdown. Broker connection close and
exact delivery-scope reconciliation precede owned DI disposal. Telemetry closes
after dependency users and its own worker joins are reconciled. Incomplete
owners remain retained and are reported as failures. See [the lifecycle
contract](LIFECYCLE.md#transaction-outbox-and-dependency-reconciliation) for the
ownership sequence and limits.
